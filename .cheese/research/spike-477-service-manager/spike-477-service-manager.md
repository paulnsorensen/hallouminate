# Spike #477: `service-manager` crate vs. the daemon's in-process restart ladder

## Recommendation

**Reject** `service-manager` (0.11.0) as a *replacement* for the current supervisor/ladder/watchdog stack. It can be evidenced as a plausible **additive** layer (crash-loop restart + boot backoff, launched by the OS instead of by re-exec) later, but as researched it cannot replace any of the three things the daemon actually needs: (1) idle-exit without a restart loop, (2) a frozen-runtime watchdog, (3) the client-spawns-daemon bootstrap model. Two of its own generated units are silently incomplete (systemd `StartLimitBurst`/`StartLimitIntervalSec` are accepted in the Rust API but never written to the unit file — confirmed in source, see evidence table), and it emits no `WatchdogSec`/`sd_notify` or launchd `Sockets`/`MachServices` support at all.

## Synthesis

`service-manager` 0.11.0 (docs.rs, last tag Feb 2026) is a thin plist/unit-file generator with `install/uninstall/start/stop/status` and a cross-platform `RestartPolicy` (`Never`/`Always`/`OnFailure`/`OnSuccess`) that maps to launchd `KeepAlive` (bool or `{SuccessfulExit}` dict — no `Crashed`, no `ThrottleInterval`, no `Sockets`/`MachServices` support) and systemd `Restart=`/`RestartSec=` (no `WatchdogSec=`, no `Type=notify`, and `StartLimitBurst=`/`StartLimitIntervalSec=` are dead-code TODOs in `RestartPolicy::OnFailure`'s systemd codegen — the crate never emits them for that variant). Both `Restart=on-failure` (systemd) and `KeepAlive{SuccessfulExit:false}` (launchd) correctly avoid respawning a daemon that exits 0 on purpose — so the "does OS-managed restart cause a loop on intentional idle-exit(0)" risk is avoidable *if* the caller wires the dict/OnFailure form, not the bare `Always`/`KeepAlive:true` form the crate defaults toward for its simplest option. Neither OS primitive detects a frozen-but-alive runtime; that requires systemd's separate `WatchdogSec=`/`sd_notify(WATCHDOG=1)` mechanism (launchd has no equivalent), and the crate wires neither. Locally, the daemon's idle-exit (`server.rs:227-263`), single-instance flock (`server.rs:719-741`), boot-backoff-on-crash-loop (`watchdog.rs:137-173`, wired at `server.rs:97-115`), and thread-based stall watchdog (`watchdog.rs:229-276`, armed at `server.rs:298-360`) are the pieces an OS-managed restart cannot subsume; only the panic-restart-with-backoff half of `supervisor.rs` (intra-process task restart, not process restart) is a plausible reason to *keep* thinking about this, and that piece is not what launchd/systemd manage at all (they only restart the whole process, not a single Tokio task inside it).

## launchd vs. systemd semantic difference table

| Concern | launchd | systemd | Daemon-relevant implication |
|---|---|---|---|
| Unconditional respawn | `KeepAlive: true` (bool) — restarts on **any** exit, including 0 | `Restart=always` — same | Would fight intentional idle-exit(0); must not use this form |
| Restart only on clean exit(0) | `KeepAlive{SuccessfulExit:true}` | `Restart=on-success` (also fires on SIGHUP/INT/TERM/PIPE unless `Type=oneshot`) | Wrong direction for idle-exit; would restart *only when* it idle-exits |
| Restart only on nonzero/crash | `KeepAlive{SuccessfulExit:false}` (nonzero exit) and/or `Crashed:true` (signal-crash) — two independently settable axes | `Restart=on-failure` (nonzero exit, signal, or timeout) — one setting covers both | This is the form compatible with idle-exit(0); the crate only emits the `SuccessfulExit` axis, never `Crashed`, so launchd-side crash-vs-clean-nonzero distinction is unavailable through the crate |
| Respawn throttle | `ThrottleInterval` (default 10s) — single flat floor | `RestartSec=` (per-attempt delay, default 100ms via the crate/systemd) + `StartLimitIntervalSec=`/`StartLimitBurst=` (rate cap over a window, config-default) | systemd's two-parameter model (delay + windowed burst cap) is strictly more expressive than launchd's one flat interval; the crate only wires `RestartSec`, never `StartLimit*`, for either OS |
| Exceeding the restart budget | No formal cap key; launchd's own heuristic ("shuts down too quickly" → job "may be suspended") is undocumented/opaque, matching the 10s note in Apple's guide | Explicit: burst exceeded ⇒ further starts denied until the interval rolls off; optional `StartLimitAction=` to escalate | The daemon's own boot-backoff (`watchdog.rs`) already gives an explicit, bounded, never-permanent policy on both OSes that neither native mechanism guarantees identically |
| On-demand / socket activation | `Sockets`/`MachServices` — declared FDs/service names, job "checks in" to inherit them | `.socket` unit + `Accept=`/`ListenStream=`, `Type=notify`/`socket` — mature, first-class | Only a real replacement for "client spawns daemon" on Linux; the crate implements neither |
| Frozen-but-alive detection | None. No heartbeat/watchdog primitive in launchd | `WatchdogSec=` + `sd_notify(WATCHDOG=1)`; timeout ⇒ SIGABRT + (per `Restart=`) restart | Only systemd has any native equivalent to the current thread-based `watchdog.rs`; launchd has nothing, so a launchd-only deployment (macOS is the primary dev/CI platform here) would regress this capability entirely if the crate/OS layer replaced the in-process watchdog |
| Readiness gating | No standard readiness protocol (informal: process must not exit within `ThrottleInterval`, no active-wait) | `Type=notify` + `sd_notify(READY=1)` — dependents wait for explicit readiness | Not currently a daemon requirement (no dependents wait on daemon readiness), but relevant if socket activation were adopted later |
| User vs. system scope | LaunchAgent (`~/Library/LaunchAgents`, runs only while user session is active) vs. LaunchDaemon (system-wide, root, boot-independent) | `systemctl --user` (session/lingering-dependent) vs. system unit | Crate's `ServiceLevel::User` maps correctly to both, but neither gives root-independent "always running across logout" without extra config (`loginctl enable-linger` on Linux; LaunchDaemon, not LaunchAgent, on macOS) — a meaningful behavior change from today's on-demand client-spawn model either way |

## Part B — code that could be removed vs. must stay

**Could plausibly be removed if OS-managed process restart were adopted** (not attempted in this spike, no source changes made):
- The *process*-level crash-loop boot-backoff bookkeeping in `crates/hallouminate-daemon/src/watchdog.rs:27-173` (`BOOT_BACKOFF_EXIT_CODE`, `check_boot_backoff`, trip-file read/write) — a systemd `StartLimitIntervalSec`/`StartLimitBurst`/`RestartSec` combination (Linux only) approximates the "escalating backoff, decays after quiet period" behavior, though not identically (systemd's is a hard deny, not an increasing floor) and the crate does not currently wire the `StartLimit*` knobs at all (see evidence table) — would require using `ServiceInstallCtx.contents` (raw override) rather than the crate's `RestartPolicy` abstraction.
- The auto-spawn path in `crates/hallouminate-daemon/src/bootstrap.rs:39-108` and the sibling-adoption polling in `crates/hallouminate-daemon/src/client.rs:71-105` — an OS-managed daemon started via `systemctl --user start`/`launchctl kickstart` (or socket activation) would not need a client to spawn it. This is the single largest behavior change and the one Conductor/worktree multi-socket model (`HALLOUMINATE_SOCKET` override, no-op in `ensure_daemon_running`, `bootstrap.rs:43-46`) most directly conflicts with: each worktree currently runs its own daemon on its own socket with no OS-manager awareness, which an OS unit (one per machine, or one per label/socket) would need to model explicitly, likely via per-worktree labels/units generated by an install command.

**Must stay regardless of adoption:**
- `crates/hallouminate-daemon/src/supervisor.rs` (intra-process task restart with backoff/intensity cap/ladder) and `crates/hallouminate-daemon/src/ladder.rs` — OS process managers restart the whole process, never a single Tokio task inside it; a single `WatcherPump` panic must not kill in-flight `Maintenance`/`CatchUp` work by tearing down the whole process.
- `crates/hallouminate-daemon/src/server.rs:227-263` (`spawn_idle_exit`) — no OS manager knows the daemon's own idle-activity clock; this is exit-code-0-on-purpose, which is exactly the case that must not be reinterpreted as a failure by whatever supervises the process.
- The thread-based stall watchdog (`watchdog.rs:229-276`, armed via `spawn_watchdog_when_armed` at `server.rs:298-360`) — launchd has no watchdog equivalent at all; systemd's `WatchdogSec=`/`sd_notify` would require rewriting the mechanism to ping via `sd_notify` (Linux-only, needs a `libsystemd`/`sd-notify` crate dependency the workspace does not currently have) and would still leave macOS with nothing, so this cannot be removed without a platform regression.
- `crates/hallouminate-daemon/src/server.rs:709-741` (`acquire_single_instance`, the flock) and the socket-cleanup ordering in `finish_shutdown`/`cleanup` — neither launchd nor systemd deduplicates across the sibling-socket-adoption scenario the wiki documents (`daemon-and-cli.md` "Sibling adoption"); this is an application-level invariant, not a process-supervision concern.

**New surface an adoption would add** (not attempted, listed for completeness): an `install`/`uninstall` CLI subcommand analogous to the existing `hallouminate hook install|uninstall` pattern (`.hallouminate/wiki/daemon-and-cli.md` CLI table); generated plist/unit content (likely via `ServiceInstallCtx.contents` raw override rather than the crate's lossy `RestartPolicy`, given the `StartLimit*`/`WatchdogSec`/`Sockets` gaps documented above); per-OS integration tests that need a real launchd/systemd (see Part C); and cargo-dist/npm distribution implications — the installed unit's `program` path must survive binary relocation/upgrade, which the current self-`current_exe()`-relaunch model (`bootstrap.rs:85-92`) does not need to solve today.

## Part C — acceptance criteria evidence source

**Evidenceable from docs/source alone (no real OS manager needed):**
- Which `RestartPolicy` variant maps to which literal plist/unit text (confirmed above by reading crate source).
- That `StartLimitBurst=`/`StartLimitIntervalSec=`/`WatchdogSec=`/`Sockets=` are absent from the crate's generated output (confirmed by `grep` on fetched source — no real daemon run needed to prove an *absence* in the generator).
- That exit-code-0 does not trigger `Restart=on-failure` or `KeepAlive{SuccessfulExit:false}` (documented systemd/launchd semantics, not implementation-dependent).

**Strictly need a real launchd/systemd run (not evidenceable from docs):**
- Whether the *installed* plist/unit actually respects `ThrottleInterval`/`RestartSec` timing in wall-clock practice (timing behavior, not just generated text).
- The `LaunchdServiceManager::status` bug (crate issue #41: reports `Stopped` for a running service on macOS) — this is an observed runtime bug, unconfirmable from source alone.
- `Disabled=true` post-install behavior for KeepAlive-bearing launchd jobs (`launchd.rs:141,180`, "prevents auto-start when KeepAlive is used... service might already be removed") — the actual `launchctl`/`launchd` state-machine interaction needs a live daemon to verify, not just the generated plist.
- Whether `systemctl --user` units survive user logout without `loginctl enable-linger` in the target environment (session/lingering behavior is host-config-dependent).
- Socket-activation wall-clock latency and correctness if that path were ever adopted (not implemented by the crate at all today, so any evidence here would require hand-written units, out of scope for this spike).

**Minimal isolated test recipe (proposed, not executed):**
1. macOS: `launchctl bootstrap gui/$UID /tmp/spike477-test.plist` with a throwaway `Label` (e.g. `com.hallouminate.spike477-test`), pointing `Program`/`ProgramArguments` at a trivial `sh -c 'exit 0'` or `exit 1` script, `KeepAlive` set via the dict form under test; observe via `launchctl print gui/$UID/<label>` and log timestamps whether/when it respawns; `launchctl bootout gui/$UID/<label>` to tear down.
2. Linux: a disposable container (or `systemd-nspawn`) running `systemd --user` (or a full system unit in a throwaway VM/container with PID 1 = systemd), install a unit generated by the crate against a trivial `exit 0`/`exit 1` test binary, `systemctl --user start`, and observe `systemctl --user status`/`journalctl --user -u <unit>` for restart timing versus `RestartSec`/`StartLimit*`.

Neither recipe was executed in this spike (explicit instruction: do not load any real launchd/systemd service on this machine).

## Open questions

- Whether a future design would use the crate's `RestartPolicy` abstraction at all, given its systemd `StartLimit*` gap and launchd's lack of a `Crashed`-key path, or bypass it entirely via `ServiceInstallCtx.contents` raw plist/unit text — the source shows both are technically possible; this repo has not decided.
- Whether OS-managed respawn would replace or supplement (not replace) the current client-spawn bootstrap model, given the multi-socket Conductor/worktree pattern documented in the wiki — the sources describe the primitives, not this repo's intended topology.
- Whether adopting `Type=notify`/socket activation is in scope at all — the crate implements neither; this is listed as an open question, not a recommendation, per the source material's "supports X or Y" framing.
